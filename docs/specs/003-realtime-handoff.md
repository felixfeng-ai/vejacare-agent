# 003 · 实时人工会话：把「刷新」变成「推送」

> 状态：**待确认**（选项未拍板，确认后才动工）
> 前置：[002-human-handoff-lifecycle.md](002-human-handoff-lifecycle.md)（回复与结单已拆开，已上线）
> 本文列了 **3 个必须你拍板的选择**（§5），其余是建议方案，你可以直接推翻。

## 1. 问题

002 把转人工的**语义**修对了：人工可以连说几句、说完显式结单。但**时效**还是错的——
两个方向都靠人肉刷新。

### 1.1 用户侧：5 秒轮询

[useChat.ts:24](../../frontend/src/hooks/useChat.ts#L24)：

```ts
/** 转人工后轮询历史消息，用于感知人工客服已回复 */
const ESCALATION_POLL_MS = 5000;
```

人工在工单台点「发送回复」之后，**用户平均要等 2.5 秒、最坏 5 秒**才看见这句话。
而这段时间输入框是锁着的（`inputLocked`），用户盯着一个不动的界面，只能怀疑是不是坏了。

### 1.2 客服侧：连轮询都没有，只有一个刷新按钮

[DeskPage.tsx](../../frontend/src/pages/DeskPage.tsx) 进页面拉一次列表、点一次拉一次详情。
用户等待期间补的订单号、地址、诉求（002 §2.3 刚修好、已经落库了）**客服不点刷新就永远看不到**。
002 给列表加了 `unread_count` 徽标——但徽标本身也得刷新才更新。**把数据修对了，人还是看不见。**

### 1.3 这件事的严重性

前面几轮的修复都受限于「线上跑 mock 模式」——只有真模型才会错的那部分验不了。
**实时通道跟模型无关**：它错了就是错了，接不接真 key 都一样。这是少数能在生产上完整验证的功能。

## 2. 目标 / 非目标

**目标**

1. 人工回复 → 用户看见：P50 < 1s，P95 < 2s（现在是 P50 2.5s / P95 5s）。
2. 用户发言 → 客服看见：P50 < 1s（现在是「有人点了刷新」）。
3. 新工单出现 → 客服看见：P50 < 1s。
4. 推送挂掉时**降级但不失效**：慢轮询兜底，功能仍可用。
5. 断线重连不丢消息、不重复渲染消息。

**非目标**

- 不做语音/视频、不做客服坐席管理、不做消息已读回执。
- 不做跨进程/跨机的推送（见 §7 已知边界）。
- 不改 `/api/chat/stream` 现有协议——它是可用的，别动。

## 3. 核心设计决策

### 3.1 推「失效信号」，不推消息体

推送的载荷是**「这个会话变了，去拉一次」**，不是消息内容本身：

```json
{ "type": "changed", "scope": "session", "session_id": "s_xxx" }
{ "type": "changed", "scope": "desk" }                    // 工单队列变了
```

**为什么**（这条是全文最重要的判断）：

- **单一读路径**。REST 接口仍是唯一的读取实现。若推送直接带消息体，就出现了第二份序列化
  逻辑，两边迟早不一致——而「推送说有、拉下来没有」正是本项目反复踩的那类坑
  （002 §2.3、工单详情缺 `unread_count`，都是同一种病）。
- **丢包不致命**。信号丢了最多是「这次没即时更新」，下一次操作或兜底轮询会补上。
  推送**不承担正确性**，只承担时效。这让整条链路可以坏而不塌。
- **服务端不需要知道订阅者能看什么**。信号里没有内容，就不存在「该不该给这个人推这条」
  的鉴权分支——少一个能写错的地方。

代价：一次变更多一次 HTTP 往返（几十毫秒）。这个代价换上面三条，值。

### 3.2 发布点必须挂在 **commit 之后**，不是写在「写消息」那一步

这是本文最容易写错的地方，也是本项目的老毛病（「接口正常返回，数据其实没落库」）的镜像版本：
**广播出去了，数据其实还没提交。**

`repository.add_message()` 只 `add`，**不 commit**——commit 由 `session_scope()` 统一做。
如果在 `add_message` 末尾就广播，订阅者收到信号、立刻开一个新事务去读，**读到的是旧数据**：

```
add_message()  →  广播 ──► 订阅者读库（此时还没 commit）→ 读到旧快照 → 什么都不显示
session_scope() 退出 → commit  ←── 真正的写入在这里
```

用户侧表现为「人工回了话，用户那边闪一下又没了」；客服侧更糟——**这条消息就此永远看不到**，
因为不会再有第二个信号来救它。

**建议做法**：`app/events.py` 里挂 SQLAlchemy 的 `after_commit` 事件，
让「写库成功」和「广播」在结构上成为同一件事。这样：

- 新增写消息的地方**不可能漏推**（它不经过别处）；
- 也不可能**早推**（commit 没成功就不广播，回滚了更不广播）。

> 这和 README「核心设计决策 1」是同一条思路：**防错要靠结构，不靠自觉。**
> 靠「记得在写完之后调一下 broadcast」的写法，第 5 个调用点就会被忘掉。

### 3.3 订阅者不得持有数据库会话

SQLite 同一时刻只允许一个写事务（002 §`_close` 已经踩过 `database is locked`）。
一条挂几十分钟的 SSE 连接若握着 `session_scope()`，**整个应用就再也写不进任何东西**。

所以：连接只持有**一个 `asyncio.Queue`**；收到信号 → 开一个短事务读库 → 关掉 → 发出去。
读完立刻放手，绝不跨 `await` 持锁。

### 3.4 通道选 SSE，不选 WebSocket

**单向不是缺陷——本项目里根本没有双向需求。**

| 客户端 → 服务端的方向 | 现在走什么 |
|---|---|
| 用户发消息 | 已有 `POST /api/chat/stream` |
| 客服回复 / 结单 | 已有 `POST /api/escalations/{id}/reply` `/close` |
| 客服拉列表 / 详情 | 已有 `GET` |

要给通道加双向，等于**把已经能用、已经测过的 HTTP 接口再实现一遍**，多出一套协议、
一套错误处理、一套测试。这不是能力，是负债。

选 SSE 的另外几个具体理由：

- **nginx 已经配好了**。[nginx-cs.veyawork.work.conf](../../deploy/nginx-cs.veyawork.work.conf)
  已经为 `/api/chat/stream` 开了 `proxy_buffering off`，SSE 直接可用。
  而那份配置**明确写着**不打算支持 WebSocket：

  ```nginx
  # 置空而不是 "upgrade"：这里不需要 WebSocket 升级，
  # 留着会让 nginx 把连接当成要升级处理
  proxy_set_header Connection        '';
  ```

  改成 WebSocket 要动这四行，加 `map $http_upgrade $connection_upgrade`，
  而这份文件是「服务器现状的准源头」、部署脚本 diff 它——改它等于改部署脚本的假设。
- **解析器已经写好了，而且处理过坑**。[sse.ts](../../frontend/src/api/sse.ts) 手写分帧，
  已经处理了「事件被切两半」「`\r\n` 被切开」「keep-alive 注释行」三种情况。
  **心跳注释行 `: ping` 现在就会被正确忽略**——长连接需要的心跳，解析侧零改动。
- **同源**，没有跨域，没有额外握手。

**两个必须处理的现实问题**：

1. `proxy_read_timeout 300s`（配置里写死）：连接最多挂 5 分钟。→ 服务端每 20s 发一行
   心跳注释，或客户端 4 分钟主动重连（建议两者都做，前者保代理，后者保端到端）。
2. **控制台的 `EventSource` 用不了**：`EventSource` 不能带 `Authorization` 头，而后台接口
   全部要求 Bearer 令牌。→ 控制台侧必须用 `fetch` + `ReadableStream`（就是现有的
   [stream.ts](../../frontend/src/api/stream.ts) 那套）。用户侧无鉴权，可以顺带也用同一套，
   **两侧一条实现**比两种机制好维护。代价是 `EventSource` 自带的断线重连要自己写
   （约 30 行：指数退避 + 重连后重新拉一次历史）。

### 3.5 保留慢轮询做兜底，不删

推送通了之后，把用户侧的 `ESCALATION_POLL_MS` 从 5s 放到 30s，**降级不清除**。

理由：推送依赖长连接，长连接依赖网络和代理的脾气。留着兜底轮询，
意味着「推送挂了」这个故障的后果是「退回到今天的行为」，而不是「功能消失」。
**能降级的功能才是能上线的功能。**

## 4. 接口设计（建议）

### 4.1 用户侧：`GET /api/sessions/{session_id}/events`

```
GET /api/sessions/s_abc123/events        Accept: text/event-stream
→ data: {"type":"hello","session_id":"s_abc123"}
→ : ping                                  （每 20s）
→ data: {"type":"changed","scope":"session"}
```

只订阅**一个会话**。不提供「订阅全部」——那是后台才需要的，且用户侧没有任何理由
接收别的会话的信号。

### 4.2 控制台侧：`GET /api/console/events`

```
GET /api/console/events                  Authorization: Bearer <token>
→ data: {"type":"hello","role":"agent"}
→ data: {"type":"changed","scope":"desk"}                    工单队列有变
→ data: {"type":"changed","scope":"session","session_id":"s_abc123"}   某个会话有变
```

复用 `require_role(ROLE_AGENT, ROLE_ADMIN)`，用**依赖项**统一挂（和 escalation 路由同样的写法：
「四个接口的可见性是同一件事，分散写就有漏网机会」）。

**注意**：SSE 是 GET，令牌走 `Authorization` 头没问题（不是 `EventSource`，是 `fetch`）。
**不要把令牌塞进 query string**——那会进 nginx 的 `access_log`，而这份日志是持久化的。

### 4.3 前端

- `useChat`：新增 `useSessionEvents(sessionId)`，`changed` → 调已有的 `loadHistory(id, true)`。
- `DeskPage`：新增 `useDeskEvents()`，`scope=desk` → `loadList()`，
  `scope=session` 且等于当前打开的详情 → `loadDetail(id)`。已有的 `detailSeqRef` 竞态保护直接复用。

## 5. 必须你拍板的三个选择

### 5.1 人工接管期间，AI 是什么档位？

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A** | **完全闭嘴**（现状） | 最简单，绝不会跟人工抢答 | 用户等待期间问「大概还要多久」也没人理；输入框锁着，像坏了 |
| **B** | **出草稿，人工按下发送才算数** | 客服效率高；AI 仍然只是工具，不直接对用户说话 | 要加草稿接口与 UI；「AI 起草、人工发送」说成「人工客服」是否诚实，需要产品上明确 |
| **C** | **AI 继续答业务问题，人工只处理例外** | 用户不空等 | 已经有两个声音了，这和「转人工」的定义冲突 |

**建议 B**，并且明确一条红线：**AI 的草稿必须经过人工的手才能发出**。
理由：人工在场时，任何自动发给用户的话都会让「人工说的」和「AI 说的」失去边界，
而这正是 002 修掉的病根（AI 把人工的占位话抄了一遍当收尾）。

### 5.2 多客服并发，防不防抢单？

现状：口令是**共享的**（[security.py](../../backend/app/security.py) 开头解释了为什么），
系统里**没有客服身份表**，`agent_name` 是前端传的字符串。所以：

- 谁在线？不知道。
- 谁接了这单？只有「最后一次回复的人」。
- 两个客服同时开一个工单、同时回复 → 两条消息都落库，**不冲突，但不协调**。

| | 做法 | 说明 |
|---|---|---|
| **A** | **不做**，明说单客服场景 | 最诚实。演示规模下这是正确答案 |
| **B** | **软认领**：点「接手」写下 `assignee`，别人看到「张三正在处理」但**仍能回复** | 防的是「撞车」，不是「越权」。实现小 |
| **C** | **强锁 + 租约**：认领带 TTL，到期自动释放 | 强锁在浏览器崩了之后会变成死锁，得靠租约兜底，复杂度陡增 |

**建议 B**。理由：软认领解决 90% 的撞车，且**故障模式是「提示不准」而不是「谁也干不了活」**。
强锁的故障模式是后者——客服电脑一重启，这单就锁死了。

### 5.3 推送的落点：只推「会话变了」，还是也推「有工单了」？

**建议都推**，但分成两个 scope（`desk` / `session`）。
只推 session 的话，客服可以一直看着一个空列表——而**新工单正是最该被立刻看到的东西**。

## 6. 验收标准（可测）

| # | 标准 | 怎么测 |
|---|---|---|
| 1 | `/api/chat/stream` 行为**不变** | 现有 127 条单测 + 契约校验必须全绿 |
| 2 | 会话事件流能建立、能收到 `hello`、20s 内收到心跳 | 契约校验新增一段 |
| 3 | `POST /reply` 之后，**同一秒内**订阅该 session 的流收到 `changed` | 契约校验：起一个读流任务，发回复，断言 1s 内收到 |
| 4 | **commit 之前不广播** | 单测：`add_message` 后不 commit → 无广播；commit 后 → 有广播 |
| 5 | 订阅者不持有 DB 会话 | 单测：挂着一条流的同时，另开事务写库**不超时** |
| 6 | 断线重连后不丢消息 | 单测：断开 → 期间写两条 → 重连 → 两条都在 |
| 7 | 推送全挂时轮询兜底仍工作 | 关掉事件流，用户侧 30s 内仍能同步到人工回复 |
| 8 | 未鉴权访问 `/api/console/events` → 401 | 鉴权用例集（现有 43 条）新增 |
| 9 | 令牌不出现在 URL / nginx 访问日志里 | 代码审查 + 抓一次 `access_log` 确认 |

第 4 条是这次的重点守卫——**它守的是全文最容易写错的那一步**。

## 7. 已知边界（要写进 README，不要假装没有）

1. **单进程内存广播**。`dict[session_id, set[Queue]]` 活在 uvicorn 进程里，
   多 worker 部署会各推各的（用户连到 A 进程、写入发生在 B 进程 → 收不到信号）。
   项目和 [`_failures` 限流表](../../backend/app/security.py) 是同一个边界，
   **沿用同一句声明**：「本项目单进程 uvicorn，够用；多进程部署会各算各的」。
   真要上多进程，下一步是 Redis pub/sub——但现在不做（YAGNI）。
2. **长连接数 ≈ 在线用户数**。同源 HTTP/1.1 下浏览器每域约 6 个并发连接，
   一个 SSE 占一个坑。演示规模无碍，**真实规模要上 HTTP/2**（nginx 一行 `http2 on`）。
3. **线上跑 mock 模式**，但本功能与模型无关，**这一条在线上是真验证过的**——
   和前面几轮的修复不同，这点值得在 README 里单独说。
4. 心跳靠**应用层注释行**，不是 TCP keepalive；中间设备掐连接只能靠重连恢复。

## 9. 不做什么，以及为什么

- **不引入 Redis / 消息队列**：单进程内存够用，引入它就是为了一个不存在的规模
  （YAGNI）。边界写清楚比架构堆上去更值。
- **不做 WebSocket**：没有双向需求（§3.4）。
- **不做推送带消息体**：会让 REST 不再是唯一读路径（§3.1）。
- **不删兜底轮询**：删了就没有降级路径（§3.5）。
- **不动 `/api/chat/stream`**：它现在是对的，改它的收益是「统一」，风险是「弄坏打字机」。
